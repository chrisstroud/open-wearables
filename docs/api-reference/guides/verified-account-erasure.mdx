---
title: Verified account erasure
description: Exact, resumable whole-account deletion for Dashboard Fitness.
---

This protocol is separate from both legacy `DELETE /users/{id}` and health-source
reset. Source reset preserves the User/profile; whole-account erasure removes
them only after cleanup is verified, and atomically saves a minimal recovery
receipt. Missing users and HTTP 404 are never completion evidence.

## Release gate

The implementation is disabled by default (`ACCOUNT_ERASURE_ENABLED=false`).
Enable only after the release operator verifies deployed migration
`c6e8a0b2d4f6`, dedicated API-key permissions, the full worker/deployment inventory,
configured and retired storage targets, provider revocation, and synthetic crash
recovery against the actual service. A test with mocked external planes is not
that operational proof.

`ACCOUNT_ERASURE_WORKER_NAMES` must contain the complete release-owned Celery
worker name set, as a JSON array. Every configured worker must respond to ping,
active, reserved and scheduled inspection. Extra or missing workers fail closed.
The set is bound to the operation and terminal receipt. Reconcile it with all
deployment services; a guessed list or one responding worker is insufficient.

All three endpoints require `X-Open-Wearables-API-Key` with the distinct
`account-erasure` scope. Ordinary API keys, source-reset keys, and developer
sessions do not confer this authority. Keep this credential server-side only.
Key provisioning and runtime enablement are separate protected release actions.

Whole-account cloud revocation currently supports WHOOP only. It first checks
the credential's exact WHOOP profile identity, then requires HTTP 204 from the
revocation endpoint. Other cloud providers fail closed; offline Apple records
with no cloud credentials can still be erased. This does not enable Apple in
Dashboard's product. Expired/invalid credentials, 401/404 responses, redirects,
asynchronous acceptance, and unknown outcomes are not revocation proof.

## Exact requests

`POST /api/v1/users/{user_id}/account-erasure/plan` accepts:

```json
{
  "protocol": "dashboard-account-erasure-v1",
  "authorization": {
    "operationId": "11111111-1111-4111-8111-111111111111",
    "actorDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  },
  "target": {"kind": "owner", "userId": "synthetic-owner", "subjectId": "synthetic-subject"},
  "account": {
    "subjectId": "synthetic-subject",
    "openWearablesUserId": "22222222-2222-4222-8222-222222222222"
  },
  "scopeFingerprint": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc"
}
```

The path UUID must match `account.openWearablesUserId`; the upstream User's
`external_user_id` must match both subject IDs. Identifiers, actor, target and
scope become one durable HMAC binding. The plan does not revoke or delete.

`POST .../erase` and `POST .../verify` require the same fields plus
`authorization.planFingerprint` (the Dashboard global plan's lowercase SHA-256).
It is bound on the first erase and cannot be substituted on retry. All responses
echo the exact request bindings. Unknown fields and protocol versions fail.

## Outcomes and recovery

- HTTP 200 `planned`: the exact plan was durably admitted; no deletion proof.
- HTTP 200 `deleted` or `already_deleted`: contains `receiptFingerprint` and
  `recordedAt` (stable UTC with microsecond precision), bound to this operation.
- HTTP 202 cleanup/verification pending: no terminal receipt. Retry the same
  operation after resolving the unavailable plane; do not invent a new target.
- HTTP 409 identity/scope/plan conflict: no deletion evidence. Reconcile the
  exact bindings before proceeding.
- HTTP 503 unavailable: no terminal proof. Worker/provider/storage uncertainty
  cannot be overridden with a success flag.

Erase commits the permanent account write fence before irreversible provider or
queue actions. The source cleanup's database-half checkpoint can resume after an
external outage. Whole-account deletion never reopens syncing. User/profile
removal and terminal receipt insertion commit together. Verify is read-only: it
checks the durable receipt, absent account and owned rows, and all current
external planes. It never removes later state to make a historical receipt pass.

Provider verification and local credential clearing commit together on the
fenced User. A retry may skip provider I/O only when this durable proof exists
and credentials remain cleared. Direct source-reset apply cannot bypass an
unverified whole-account provider fence. A process crash after WHOOP revokes but
before local proof commits remains uncertain and needs reconciliation; never
invent a successful receipt or manually clear the fence to make it pass.

Receipts retain operation UUID, upstream UUID, keyed bindings, reviewed digests,
keyed locator proof, state and timestamp—not names, email, tokens, raw health
records or full requests. Protect this recovery metadata and its signing key.
Downgrade refuses to discard existing operation rows; an explicit, reviewed
recovery disposition is required before removing the schema.

## Local evidence limits

The isolated PostgreSQL/HTTP suite covers exact authorization, idempotency,
whole-account/profile removal, peer preservation, failed provider deregistration,
failed external cleanup after the database half, write-fence enforcement,
timestamp-stable terminal replay and later verification failure. Separate pure
tests reject partial worker responses. External provider, Redis, object-store and
worker behavior is simulated in that suite. Complete real-service synthetic
rehearsal before production activation or claiming the integration is certified.
